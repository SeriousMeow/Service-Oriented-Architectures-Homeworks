# RFC: Архитектура маркетплейса

## 1. Обзор системы

Маркетплейс - цифровая платформа, на которой продавцы размещают товары, а покупатели могут оформлять заказы.

**Ключевая функциональность:**
- Персонализированная лента товаров на основе истории пользователя
- Управление каталогом товаров
- Управление пользователями (покупатели и продавцы)
- Корзина и оформление заказов
- Расчет и учет платежей
- Уведомления о статусах заказов

## 2. Архитектурный стиль

**Микросервисная архитектура** с мелкозернистой декомпозицией и единой точкой входа через API Gateway.

**Обоснование:** Каждый сервис отвечает за отдельный бизнес-домен, имеет собственное хранилище данных и может масштабироваться независимо.

## 3. Декомпозиция на сервисы

| Сервис | Ответственность | База данных |
|--------|----------------|-------------|
| API Gateway | Точка входа, маршрутизация запросов | - |
| Auth Service | Аутентификация (вход по SMS), проверка доступов | PostgreSQL |
| User Service | Управление профилями покупателей и продавцов | PostgreSQL |
| Product Catalog Service | Управление товарами, категориями, атрибутами | PostgreSQL |
| Recommendation Service | Персонализация ленты на основе истории заказов | - |
| Cart Service | Управление корзиной покупателя | Cassandra |
| Order Service | Создание и управление заказами | PostgreSQL |
| Payment Service | Расчет стоимости, учет платежей | PostgreSQL |
| Notification Service | Отправка уведомлений о статусах | - |
| Personal Data Service | Обмен персональных данных на обезличенные ID | PostgreSQL |

## 4. Описание сервисов

### API Gateway

Является точкой входа для всех запросов в систему. Взаимодействует с Auth Service для аутентификации пользователя и получения его доступов. На их основе определяет, какие ручки и методы доступны пользователю.

Доступы:
- Покупатель - доступна функциональность просмотра товаров, работы с корзиной и оформления заказов
- Продавец - доступна функциональность управления товарами
- Администратор - доступна вся функциональность (включая служебную). Используется техподдержкой и командой разработки для решения проблем и управления системой

#### Где хранить доступы?

##### Вариант 1. В сервисе с данными о профилях пользователей

Плюсы:
- Вся информация о пользователе находится в одном месте
Минусы:
- Необходимо постоянно ходить в два сервиса
- Информация о доступах нужна только для API Gateway
- Работоспособность всей системы зависит от сервиса пользователей, который будет постоянно меняться

Данный вариант плох тем, что данные сохраняются там, где они не используются для обработки.


##### Вариант 2. В этом же сервисе

Плюсы:
- Данные хранятся близко
- Сервис надежнее, поскольку не требует крупных правок (только добавление новых ручек)
Минусы:
- Нужно подключать БД к API Gateway

Главная проблема этого варианта - необходимость поддерживать еще одну БД.

##### Вариант 3. В сервисе Auth Service

Плюсы:
- Сервис будет меняться очень редко, поскольку его не затрагивает разработка, что повышает его надежность
- Можно использовать существующую БД

---

Вариант 3 является наилучшим, поскольку является наиболее надежным и не требует дополнительной БД.

### Auth Service

Сервис хранит учетные данные пользователей, необходимые для аутентификации. Также он хранит уровень доступа (покупатель/продавец/администратор). При аутентификации взаимодействует с внешним SMS-сервисом для отправки одноразовых кодов.

**Процесс аутентификации:**
1. Пользователь отправляет номер телефона
2. Auth Service генерирует одноразовый код и отправляет через внешний SMS-сервис
3. Пользователь вводит полученный код
4. Auth Service проверяет код и выдает JWT токен с информацией о доступах

Номер телефона хранится в Personal Data Service, а Auth Service работает только с обезличенным идентификатором пользователя.

### User Service

Управляет профилями пользователей (покупателей и продавцов). Хранит информацию о профиле: имя, адрес доставки, историю активности, почту для отправки уведомлений. Персональные данные не хранятся открыто, используются обезличенные идентификаторы из Personal Data Service.

Не хранит доступы пользователей - они находятся в Auth Service.

### Product Catalog Service

Управляет каталогом товаров, категориями и атрибутами. Продавцы через этот сервис создают, редактируют и удаляют товары. Покупатели используют его для поиска и просмотра товаров.

Для хранения фотографий используется Media Storage на основе S3. Это позволяет надежно хранить больше количество ихображений.

Чтобы не перегружать сервис продуктов изображения загружаются на фронтед напрямую с S3. Записть фотографий происходит с сервиса продуктов, чтобы можно было обработать изображения перед сохранением и, например, проверить их на безопасность.

### Recommendation Service

Формирует персонализированную ленту товаров для каждого пользователя. Получает данные о товарах из Product Catalog Service и историю заказов из Order Service. На основе этой информации формирует рекомендации.

Сервис не имеет собственной БД - использует данные из других сервисов.

### Cart Service

Управляет корзиной покупателя. Использует **Cassandra** для хранения корзин из-за высокой частоты изменений (добавление/удаление товаров).

При добавлении товара в корзину проверяет его доступность через Product Catalog Service.

#### Где хранить корзину?

##### Вариант 1. В PostgreSQL

Плюсы:
- Простота реализации
- ACID гарантии

Минусы:
- Высокая нагрузка на запись (пользователи часто меняют корзину)
- Сложнее горизонтально масштабировать

##### Вариант 2. В Cassandra

Плюсы:
- Высокая пропускная способность на запись
- Отличное горизонтальное масштабирование
- Корзина - это сессионные данные, строгая консистентность не критична

Минусы:
- Дополнительная технология в стеке
- Eventual consistency

---

Вариант 2 (Cassandra) является предпочтительным, поскольку корзина - это данные с высокой частотой изменений и требованиями к масштабируемости. При этом гарантированная строгая консистентность не важна.

### Order Service

Создает и управляет заказами. При создании заказа:
1. Получает содержимое корзины из Cart Service
2. Инициирует платеж через Payment Service
3. Отправляет событие в Notification Service для уведомления пользователя

Хранит заказы, позиции заказов и историю статусов в PostgreSQL. Внутри с помощью компонентов с переодическим запуском отслеживает статус заказа и при необходимости отсылает уведомление.

### Payment Service

Рассчитывает стоимость заказа и обрабатывает платежи. Интегрируется с внешней платежной системой для проведения транзакций.

**Важно:** Маркетплейс не хранит данные банковских карт пользователей. Вся обработка платежей происходит на стороне внешней платежной системы. Payment Service получает только результат транзакции (успех/неудача) и сохраняет информацию о платеже в своей БД.

Это упрощает обеспечение безопасности системы.

### Notification Service

Отправляет уведомления о статусах заказов пользователям. Получает события от Order Service.

Для отправки уведомлений:
- Получает контактные данные (email) из Personal Data Service по обезличенному ID
- Отправляет email через внешний Email-сервис

Сервис не имеет собственной БД, работает реактивно на события. Может логировать отправленные уведомления для аудита.

### Personal Data Service

Обеспечивает изоляцию персональных данных и исполнение требований местного законодавтельва о хранении ПД. Хранит email, номера телефонов и прочие чувствительные данные, обменивая их на обезличенные идентификаторы для использования в других сервисах.

**Принцип работы:**
- При регистрации/обновлении пользователя сервисы отправляют персональные данные в Personal Data Service
- Personal Data Service возвращает обезличенный ID
- Другие сервисы работают только с обезличенным ID
- При необходимости (например, для отправки уведомлений) сервисы запрашивают персональные данные по ID

Это обеспечивает минимизацию доступа к персональным данным и упрощает соблюдение требований защиты данных.

## 5. Ключевые архитектурные решения

### Выделение Personal Data Service

**Решение:** Выделение хранения персональных данных в отдельный сервис.

**Обоснование:** Соблюдение требований законодательства и минимизация доступа к чувствительным данным. Сервис обменивает персональные данные на обезличенные идентификаторы для использования в других сервисах. Это упрощает аудит доступа к персональным данным и реализацию права на удаление данных.

### Хранение доступов в Auth Service

**Решение:** Информация о доступах пользователей (покупатель/продавец/администратор) хранится в Auth Service.

**Обоснование:**
- Auth Service - стабильный сервис, который редко меняется
- Доступы используются только для аутентификации и авторизации
- Не требуется дополнительная БД (используется существующая БД Auth Service)
- Повышается надежность системы за счет изоляции критичной функциональности

### Cassandra для Cart Service

**Решение:** Использование Cassandra для хранения корзин.

**Обоснование:**
- Высокая пропускная способность на запись (частые изменения корзины)
- Сессионные данные, не требующие строгой консистентности
- Горизонтальное масштабирование под высокую нагрузку

### PostgreSQL для транзакционных данных

**Решение:** PostgreSQL для Order Service, Payment Service, User Service, Auth Service, Product Catalog Service.

**Обоснование:**
- ACID гарантии критичны для заказов и платежей
- Поддержка транзакций и внешних ключей
- Надежность и зрелость технологии

### gRPC для внутренней коммуникации

**Решение:** Синхронное взаимодействие между сервисами через gRPC.

**Обоснование:**
- Высокая производительность (protobuf, HTTP/2)
- Типобезопасность (схемы .proto)
- Автогенерация клиентов и серверов

### Аутентификация через SMS-код

**Решение:** Вход в систему осуществляется через подтверждение одноразового кода из SMS, отправленного на номер телефона пользователя.

**Обоснование:**
- Безопасность: нет паролей, которые можно украсть
- Удобство: пользователю не нужно запоминать пароль
- Привязка к телефону упрощает восстановление доступа

### S3 для Media Storage

**Решение:** Использование S3-совместимого хранилища для фотографий товаров.

**Обоснование:**
- Масштабируемое объектное хранилище
- Оптимизировано для больших объемов файлов

### Делегирование обработки платежей

**Решение:** Обработка платежей полностью делегирована внешней платежной системе. Маркетплейс не хранит данные банковских карт.

**Обоснование:**
- Упрощение безопасности системы
- Снижение рисков утечки финансовых данных

## 6. Владение данными

**Принцип:** Каждый сервис владеет своими данными. Нет shared databases между сервисами.

**Взаимодействие:** Сервисы получают данные друг от друга только через API (синхронное gRPC).

| Сервис | Владеет данными |
|--------|----------------|
| Auth Service | Учетные данные, роли/доступы пользователей |
| User Service | Профили пользователей (имя, адрес, история активности) |
| Product Catalog Service | Товары, категории, атрибуты, остатки |
| Cart Service | Корзины пользователей |
| Order Service | Заказы, позиции заказов, статусы |
| Payment Service | Транзакции, счета, информация о платежах |
| Personal Data Service | Персональные данные пользователей |

## 7. Внешние интеграции

| Система | Назначение | Особенность |
|---------|------------|-------------|
| **Платежная система** | Обработка платежей | Маркетплейс не хранит данные карт пользователей |
| **Email сервис** | Отправка email уведомлений | Используется Notification Service |
| **SMS сервис** | Отправка SMS | Используется Auth Service |

## 8. Безопасность

**Делегирование обработки платежей:** Данные банковских карт обрабатываются внешней платежной системой. Маркетплейс получает только результат транзакции. Это снижает исключает возможность утечки данных карт со стороны маркетплейса.

**Изоляция персональных данных:** Personal Data Service хранит чувствительные данные пользователей отдельно. Другие сервисы работают только с обезличенными ID.

**Аутентификация без паролей:** Использование SMS-кодов устраняет риски утечки паролей и их компрометации.
